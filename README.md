# dimagh

**Inside the living mind.** An interactive, systems-level simulation of what
happens inside the human brain during perception, attention, memory, emotion,
language, movement and sleep.

The central idea: don't just show the brain — show the brain *doing something*.
Ask "what happens when I see a red apple?" and watch a simplified model of that
cascade unfold spatially and temporally through a 3D brain, on a timeline you
can scrub, reverse and interrogate.

> **This is an educational visualisation, not a medical device.** Every value,
> level and glow is generated by a scenario file in `data/`. Nothing is recorded
> from a brain, nothing is measured about the viewer, and no number shown is a
> clinical or physiological measurement.

---

## Running it

```bash
pnpm install
pnpm dev          # http://localhost:3000
pnpm build        # production build
pnpm typecheck    # tsc --noEmit (no ESLint config is shipped)
```

No API keys. No backend. No database. No accounts. Every byte of data is bundled
with the page and the whole experience keeps working if the network disappears
after the first load.

To run a production build while `pnpm dev` is holding `.next`:

```bash
DIMAGH_DIST=.next-build pnpm build
DIMAGH_DIST=.next-build pnpm start
```

Deploys to Vercel with no configuration.

## Architecture

The guiding constraint: **scenarios are data, not code.** Adding a new process
to the product means adding a JSON file, not writing animation code. Eleven very
different scenarios share one player with no per-scenario branching in the
components.

```
data/
  brain/regions.json          35 regions: position, category, role, systems, caveat
  brain/connections.json      79 conceptual pathways with direction and profile
  scenarios/*.json            11 scenarios: events, stages, causal chain, science
  experiments/illusions.json  8 perceptual demonstrations

lib/
  brain/atlas.ts              resolves the JSON once at module load: mirrored
                              region instances, Bézier pathway geometry, adjacency
  simulation/engine.ts        evaluate(scenario, time, params) → SimFrame
  simulation/clock.ts         playback time, deliberately outside React
  visualization/              procedural geometry, GLSL, camera rig, render bridge

components/
  brain/                      the seven render layers
  simulation/                 timeline, transport, explanation, causal explorer
  scenarios/                  one interactive task per scenario
  experiments/                one component per illusion
```

### Four decisions worth knowing about

**1. The engine is a pure function of time.**
`evaluate(scenario, t, params)` integrates nothing frame to frame. That is the
whole reason scrubbing, reversing and jumping to an arbitrary timestamp produce
exactly the state the timeline claims. Signal particle positions are computed on
the CPU for the same reason — baking birth times into instanced attributes would
be cheaper and would break the moment you drag the playhead backwards.

**2. Per-frame state never touches React.**
Playback time lives in a module singleton (`lib/simulation/clock.ts`) that
notifies the DOM on a ~16 Hz throttle. The WebGL layers read `clock.time`
directly inside `useFrame`. One component (`SimDriver`) evaluates the simulation
each frame and writes the result into shared typed arrays that are *the same
objects* the shaders use as uniform values — so there is no copying, no
per-frame allocation and no re-render anywhere in the tree.

**3. The brain is generated, not loaded.**
`lib/visualization/brainGeometry.ts` builds the mesh procedurally: an
anatomically-inspired envelope with the longitudinal, lateral and central sulci
cut explicitly, then multi-scale ridged noise for the gyri. No licensing
question, and the mesh carries the extra per-vertex data the shaders need (fold
depth, hemisphere, lobe). The activity field is accumulated per *vertex* in the
shell shader — a 35-iteration loop at fragment rate would be far too expensive,
and a soft glow interpolates perfectly.

**4. The camera is a rig, not OrbitControls.**
A scripted cinematic move and a user drag both want to own the camera
transform. `lib/visualization/cameraRig.ts` owns one spherical state that both
GSAP timelines and pointer input write to, with a separate "current" state
chasing the goal every frame — which gives drag inertia and means a scripted
tween can never snap.

### The seven render layers

| Layer | Component | Notes |
|---|---|---|
| 1 Anatomy | `BrainModel` | cortex, cerebellum, brainstem; one shared shell material |
| 2 Regions | `RegionMarkers` | one InstancedMesh; `instanceMatrix` so raycasting works |
| 3 Pathways | `BrainConnections` | ~150 tubes merged into one draw call; state via a 128×1 data texture |
| 4 Signals | `SignalParticles` | pooled billboards, CPU-positioned for scrub accuracy |
| 5 Activity field | `BrainModel` | surface + inner volume, accumulated per vertex |
| 6 Labels | `LabelProjector` → `BrainLabelOverlay` | real DOM, moved imperatively — never canvas text |
| 7 Environment | `AmbientEnvironment`, `NeuralDust` | gradient backdrop; GPU-animated particle field |

## Scientific positioning

This is the part the project is built around, not an afterthought.

- Every claim is tagged **KNOWN** / **SIMPLIFIED** / **CONCEPTUAL**, and the
  complete ledger is inspectable at `/science`.
- Each region records the functional systems it participates in — never exactly
  one — plus a `caveat` field stating what the visual abstraction hides.
- No region is described as doing one thing. The amygdala is not "the fear
  centre"; the hippocampus does not "store memories".
- Timings are stretched so the cascade can be watched. The ordering is
  meaningful; the absolute durations are not.
- Lab outputs are explicitly **conceptual indices on a 0–100 scale**, computed
  from dials by coefficients in the scenario file. They are not measurements and
  not predictions about anyone.
- Where a framing is contested in the field (predictive processing, what
  readiness potentials imply about agency, how hippocampus-independent a
  consolidated memory becomes), the project says so rather than quietly picking
  a side.

## Accessibility & performance

- Every explanation exists as real DOM text. WebGL enhances the explanation; it
  is never the only route to it.
- `prefers-reduced-motion` is honoured and manually overridable: camera cuts
  instead of flying, particle drift nearly stops, post-processing is skipped,
  and the motion-aftereffect experiment refuses to run and says why.
- Full keyboard transport (space, J/L, R, F), an ARIA slider timeline with
  arrow/Home/End, visible focus throughout, and a skip link.
- Render budget is detected per device and user-overridable across three tiers,
  controlling particle counts, mesh subdivision, DPR and post-processing.
- Instancing, merged geometry, data textures, dynamic imports per scenario and
  per illusion, and IntersectionObserver-gated card motifs.

## Privacy

No account, no login, no analytics, no telemetry, no backend, no cookies. The
reaction times you generate in the Stroop task and the answers you give in the
recall task stay in your browser and are never transmitted anywhere.
